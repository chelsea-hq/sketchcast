### Webhooks and third-party intake

None detected; no webhook or provider intake changed. The recorder's browser
event boundary now distinguishes failure from successful completion.
The current W3C working draft describes an error followed by collected data and
a stop event, so a stop event alone cannot establish a successful take.
[MediaStream Recording, error handling](https://www.w3.org/TR/mediastream-recording/#error-handling).

At `lib/recorder.ts:94`, an attempt-local failure flag and recorder-identity
checks guard data, error, and stop callbacks. The failure path detaches handlers,
stops an unexpectedly active encoder, discards chunks, clears the active recorder, and releases owned capture before
calling the error callback. Saved stale callbacks are also harmless because
their closure checks still run. Browser error details are not sent over the
network or rendered by Studio.

### AI-generated code patterns

The review traced failure paths and side effects rather than relying on a green
aggregate test count:

- `components/Studio.tsx:249` rejects canvas changes while a saved project is
  still pending restoration. `restoreProject` sets the saved scene before
  applying it, then clears pending state at `components/Studio.tsx:169`.
- `components/Studio.tsx:893` completes the save and subsequent project-list
  read before changing pending state, clearing the canvas API, restoring
  readiness, and selecting home. There is no further awaited operation between
  those mutations and the view transition. A rejected save/read reaches the
  existing catch without taking that success path.
- `saveActiveProject` clears its pending timer and awaits the existing vault
  write. The immediate storage neighbor still resolves writes on transaction
  completion (`lib/recovery-vault.ts:117`).
- Board's existing unmount cleanup disposes its scheduled API gate at
  `components/Board.tsx:40`; the gate rejects delivery after disposal. An API
  arriving during the awaited storage work is cleared after that work finishes.
- Recorder failure releases only recorder-owned canvas video tracks at
  `lib/recorder.ts:152`. The existing live-session microphone remains owned by
  its camera/microphone session. This does not grant a new media permission.
- Studio's error callback resets recording and prompter playback without calling
  `persistTake`, creating a Blob URL, or announcing a successful take.
