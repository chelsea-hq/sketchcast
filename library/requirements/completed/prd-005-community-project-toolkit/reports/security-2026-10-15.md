## Findings detail

### SEC-005-01 [HIGH] Unpatched braces remains in the dependency graph

- **Location:** `package-lock.json:4928`; `package.json:25` (`audit:all`).
- **Surface:** dependency supply chain.
- **Evidence:** the locked entry is `braces@3.0.3`. The dependency agent's full
  audit exits 1 with 8 High / 3 Low package records, and the production-only
  audit exits 1 with 4 High / 3 Low package records. These are affected package
  counts, not separate exploit families.
- **Description:** deeply nested attacker-controlled brace patterns can
  exhaust recursive walkers. The advisory lists no patched release. The
  dependency paths are Excalidraw → Sass → Chokidar → braces and Next's ESLint
  plugin → fast-glob → micromatch → braces. [GitHub advisory](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm).
- **Reachability:** no direct application imports of braces, Sass, Chokidar,
  fast-glob, or micromatch were found in `app`, `components`, `lib`, or `scripts`.
  The parent's clean-source Next 16.3.8 webpack build later became available.
  All 22 production `.nft.json` traces were inspected: none referenced braces,
  Sass, Chokidar, fast-glob, or micromatch. This supports limited production
  server reachability, but does not waive the full contributor/build dependency
  gate or prove every future bundling path safe. No hostile recursion stress
  test was run.
- **Remediation:** await a patched supported graph or prepare an independently
  reviewed compatible dependency replacement. Do not use the proposed editor/
  framework downgrade or weaken the audit threshold to produce a green gate.
- **Status:** unresolved; release and formal Security-to-Quality gate blocked.

### SEC-005-02 [MEDIUM] Compressed image files lacked an aggregate decode budget

- **Location before fix:** `lib/project-file.ts:269` (`imageFile`),
  `lib/project-file.ts:297` (up to 500 file entries).
- **Surface:** untrusted input / browser availability.
- **Evidence:** a parser-only synthetic reproduction built valid CRC PNGs at
  4,000 × 4,000 pixels and referenced 100 unique file IDs. The 2,101,179-byte
  JSON file was accepted, representing 1.6 billion pixels, approximately
  6.4 GB if all decoded as RGBA. The old checks limited each file to 40 MP,
  not the combined project. No large browser decode was attempted; actual
  browser memory/cache behavior was not measured.
- **Remediation:** count unique referenced images before persistence/rendering;
  cap combined pixels at 40 million and decoded base64 payload bytes at 6 MiB.
  Reusing one file in multiple image elements counts it once; unused images
  remain excluded from portable output.
- **Status:** fixed and re-evaluated. The final checks at
  `lib/project-file.ts:358` reject the original synthetic amplification payload
  before persistence or image decoding.

### SEC-005-03 [MEDIUM] Tiny files could request excessive hatched geometry

- **Location before fix:** `lib/project-file.ts:6` (`MAX_COORDINATE`),
  `lib/project-file.ts:150` (shape dimensions),
  `components/ProjectPreview.tsx:20` (render call).
- **Surface:** untrusted input / browser availability.
- **Evidence:** a 381-byte file containing one filled cross-hatched rectangle
  with width/height 1,000,000 and stroke width 1 passed validation. Installed
  Excalidraw sets `hachureGap = element.strokeWidth * 4`
  (`dist/dev/chunk-4FTI6OG3.js:9531`); Rough.js scans the original geometry.
  The preview's 480-pixel output cap does not bound that shape-generation work.
  Safe bounded Rough.js samples produced 2,840 drawing operations for a
  1,000-square shape and 14,128 for a 5,000-square shape. Extrapolation to
  accepted million-unit shapes indicates excessive work; those large cases
  were deliberately not rendered.
- **Remediation:** reject impractical shape/point extents and enforce a shared
  conservative hatch-work budget before calling the renderer. Account for
  narrow/zero-width strokes, cross-hatch/zigzag, and repeated intersections in
  filled paths. Reject with a clear error rather than silently altering boards.
- **Status:** fixed and re-evaluated. The final implementation uses a 16,384
  maximum element dimension and actual point extent, ±100,000 scene
  coordinates, and 20,000 aggregate estimated hatch segments at
  `lib/project-file.ts:239`. It accounts for repeated path intersections and
  rejects the original giant shape. This is a conservative work estimate, not
  a universal browser memory guarantee.

### SEC-005-04 [LOW] Conditional KaTeX prototype-pollution gadget remains

- **Location:** `package-lock.json:8162`; `lib/board-actions.ts:31` and `:93`.
- **Surface:** diagram-renderer dependency.
- **Evidence:** locked `katex@0.16.47` is below the patched 0.18.2 line; the
  current Mermaid dependency range does not admit that release. Exploitation
  requires prior prototype pollution or control over option prototypes;
  KaTeX does not supply the initial pollution. [GitHub advisory](https://github.com/advisories/GHSA-238p-pmpm-9mq7).
- **Reachability:** application Mermaid conversion is reachable. Installed
  Mermaid defaults to `securityLevel: "strict"`, uses
  `renderKatexSanitized` for math dimensions, and sanitizes final SVG with
  DOMPurify before the converter inserts it. The new project-file parser
  rejects prototype keys and does not pass renderer options through. No
  prerequisite pollution or standalone diagram-input exploit was demonstrated.
- **Remediation:** maintain the tracked follow-up for a compatible patched
  Mermaid/KaTeX graph with diagram/math browser coverage. Do not assert that
  sanitization eliminates every potential pre-existing pollution path.
- **Status:** documented Low follow-up, owner PRD 005; review by 2026-10-22.
